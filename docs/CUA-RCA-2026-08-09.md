# BridgeSessions macOS CUA — Deep RCA + Install/Activate/Menubar Design

**Date:** 2026-08-09  
**Author:** Hermes Agent (peer-linux-a)  
**Scope:** Full root-cause analysis of `bs cua` failures on macOS, binary/source divergence, TCC permission persistence, and design for a proper install → activate → menubar helper workflow.

---

## Executive Summary

macOS CUA is broken by **six compounding defects** spanning three layers (wire protocol, source control, and OS permissions). The helper code works mechanically — we proved it by manually sending the correct wire format — but the daemon never successfully calls it due to a protocol mismatch that exists only in the running binary, not in source. Meanwhile, TCC permissions silently vanish because the binary is adhoc-signed with no stable identity. The fix requires: (1) aligning the wire protocol, (2) committing the macOS helper dispatch code to source, (3) shipping a proper `.app` bundle with stable signing, and (4) a menubar helper for user-facing install/activate/status.

---

## Layer 1: Wire Protocol Mismatch (BUG — code)

### What happens

The daemon's `cua_helper_rpc()` (bs-protocol.h:2980–2990) sends the auth token **inside the JSON body**:

```
{"action":6,"x":0,"y":0,"button":0,"hid_key":0,"modifiers":0,"text":"","token":"2b1bdb77..."}\n
```

The helper's server loop (bs-cua-helper.h:354–358) expects the token as a **space-separated prefix**:

```
2b1bdb77... {"action":6,"x":0,"y":0}\n
```

The helper reads the first space-delimited token, compares it to the real token, and gets `{"action":6,...` instead of the hex token → returns `{"status":1,"error":"auth"}`.

### Proof

Manual test with the correct (prefix) format:
```bash
TOKEN=$(cat ~/.bridgesessions/cua-helper-token)
printf '%s {"action":6}\n' "$TOKEN" | nc -w 5 127.0.0.1 19986
# → {"error":"screencapture failed — grant Screen Recording to the helper (TCC)","format":0,"screen_h":0,"screen_w":0,"status":1}
```

The helper **accepted the auth** and tried to capture — it just failed on TCC (Layer 3). With the JSON-embedded format the daemon uses:
```bash
echo '{"action":6,"token":"2b1bdb77..."}' | nc -w 5 127.0.0.1 19986
# → {"status":1,"error":"auth"}
```

### Fix

**Option A (minimal):** Change `cua_helper_rpc()` to send `TOKEN {json}\n`:
```cpp
// bs-protocol.h, cua_helper_rpc(), replace lines 2980–2990:
nlohmann::json j;
j["action"]  = req.action;
j["x"]       = req.x;
j["y"]       = req.y;
j["button"]  = req.button;
j["hid_key"] = req.hid_key;
j["modifiers"] = req.modifiers;
j["text"]    = req.text;
// Token as space-prefix, NOT inside JSON (helper expects "TOKEN {json}\n")
std::string line = token + " " + j.dump() + "\n";
```

**Option B (alternative):** Change the helper to accept token inside JSON. Less preferred — the prefix format is simpler and avoids leaking the token into parseable JSON.

**Recommendation: Option A.** The helper's format is already correct; the daemon side is the one that diverged.

## Layer 2: Source/Binary Divergence (BUG — source control)

### What happens

The main branch source (`bs-protocol.h:3104–3107`) has a **stub** for macOS:

```cpp
#elif defined(__APPLE__)
    resp.status = 1;
    resp.error = "macos CGEvent not yet deployed (P5c)";
    return resp;
```

This stub **never calls `cua_helper_rpc()`**. But the binary running on peer-mac (`9a8b229c`, 2,337,280 bytes, dynamic Mach-O) **does** call the helper — we proved this with `strings`:

```
$ strings ~/.local/bin/bridgesessions | grep -i "cua-helper"
macos CUA input requires cua-helper (run: bridgesessions --cua-helper in user session)
--cua-helper
/cua-helper-token
no cua-helper token
empty cua-helper token
cua-helper not running (connect failed)
cua-helper send failed
cua-helper no response
```

The string `"macos CUA input requires cua-helper"` **does not exist in any branch** of the source repo (checked: `main`, `release/2.0.19-alpha7`, `audit/public-2.0.5-alpha2`). The peer-mac binary was built from **uncommitted/lost source** that implemented the macOS helper dispatch but was never committed.

### The macOS helper code DOES exist in source

The actual helper implementation (`cua_helper_execute()` in `bs-cua-helper.h:170–293`) is complete and correct for macOS:
- Action 0: `CGDisplayBounds` screen info ✓
- Action 1: `CGEventCreateKeyboardEvent` key press ✓
- Action 2: `CGEventKeyboardSetUnicodeString` text entry ✓
- Action 3: `CGEventCreateMouseEvent` mouse move ✓
- Action 4: mouse button down/up ✓
- Action 5: `CGEventCreateScrollWheelEvent` wheel ✓
- Action 6: `screencapture -x` CLI capture ✓

The problem is that `cua_execute()` (the daemon-side dispatcher) **never calls** `cua_helper_rpc()` on macOS — it hits the stub and returns immediately. The Windows path (lines 3094–3103) correctly tries the helper first:

```cpp
// Windows path (CORRECT — tries helper first):
auto helper_resp = cua_helper_rpc(req, app_home);
if (helper_resp.status == 0) return helper_resp;
// fall through to fallback...
```

### Fix

Replace the macOS stub in `cua_execute()` with the same helper-first pattern used by Windows:

```cpp
#elif defined(__APPLE__)
    // macOS: try the cua-helper first (runs in user session for desktop access)
    {
        auto helper_resp = cua_helper_rpc(req, app_home);
        if (helper_resp.status == 0) return helper_resp;
        // Fall through to in-process fallback if helper not running
    }
    // In-process fallback: ScreenCaptureKit for capture, CGEvent for input
    // (only works if daemon itself runs in the user session)
    if (req.action == 6) {
        // Use bs_macos_capture_png (macos-capture.mm / ScreenCaptureKit)
        char tmp[] = "/tmp/bs-cua-XXXXXX.png";
        int fd = mkstemps(tmp, 4);
        if (fd >= 0) { close(fd); }
        char err[1024] = {};
        if (bs_macos_capture_png(tmp, 0, err, sizeof(err))) {
            std::ifstream cap(tmp, std::ios::binary | std::ios::ate);
            auto sz = cap.tellg();
            if (sz > 0 && (size_t)sz <= MAX_IMAGE_BYTES) {
                resp.data.resize((size_t)sz);
                cap.seekg(0);
                cap.read((char*)resp.data.data(), sz);
                resp.format = 1; resp.status = 0;
                auto r = CGDisplayBounds(CGMainDisplayID());
                resp.screen_w = (int16_t)r.size.width;
                resp.screen_h = (int16_t)r.size.height;
            }
        }
        ::unlink(tmp);
        if (resp.status != 0) {
            resp.status = 1;
            resp.error = std::string("macOS capture failed: ") + err;
        }
        return resp;
    }
    // For non-capture actions without helper, return error
    resp.status = 1;
    resp.error = "macOS CUA input requires cua-helper (run: bridgesessions --cua-helper in user session)";
    return resp;
```

### Also: `screen` vs `capture` inconsistency

`bs cua screen peer-mac` returns `0x0` with exit 0 (appears to succeed with empty dimensions). This is because action=0 (screen_info) hits the macOS stub, returns `status=1, error="macos CGEvent not yet deployed"`, but the client-side code for `screen` interprets `status=1` as "return 0x0" instead of propagating the error. `capture` correctly surfaces the error string.

**Fix:** Client-side `cua screen` should check `status` and print the error if non-zero, same as `capture` does.

## Layer 3: TCC Permission Persistence (BUG — signing/identity)

### What happens

The TCC database on peer-mac has **zero entries** for Screen Recording or Accessibility:

```sql
SELECT service, client, auth_value FROM access 
WHERE service IN ('kTCCServiceScreenCapture','kTCCServiceAccessibility');
-- (empty result set)
```

The user says "I granted permissions many times." The grants are not persisting because:

1. **The binary is adhoc-signed** — `codesign -dv` shows `flags=0x20002(adhoc,linker-signed)`. macOS TCC tracks permissions by the binary's code signature identity (CDHash). An adhoc signature has no stable identity — every rebuild produces a different CDHash.

2. **Binary replacement invalidates grants** — When the binary at `~/.local/bin/bridgesessions` is replaced (e.g., during a fleet deploy), the CDHash changes. macOS silently invalidates the old TCC grant. The user grants permission, then the next deploy wipes it.

3. **No stable bundle identifier** — The Info.plist has `com.minddragon.bridgesessions` but the adhoc signature uses `Identifier=bridgesessions` (no bundle ID). TCC needs a stable bundle ID to persist grants across binary updates.

4. **The helper runs as a separate process** — `bridgesessions --cua-helper` is the same binary file. macOS may prompt separately for the helper process vs the daemon process, creating confusion about which one needs the grant.

### Fix

**Short-term:** Create a proper `.app` bundle with:
- A stable `CFBundleIdentifier` (e.g., `com.minddragon.bridgesessions`)
- Adhoc-signed but with a **stable signing identity** (same CDHash every build — use `codesign -s -` with a fixed provisioning profile, or self-sign with a local certificate)
- The helper launched from within the `.app` bundle so macOS sees a consistent path + identity

**Long-term:** Developer ID certificate + notarization. The repo already has `scripts/sign-macos.sh` and `scripts/notarize-macos.sh` — they just need a real Developer ID certificate.

**TCC grant script (for setup):**
```bash
# Grant Screen Recording + Accessibility to the .app bundle
sudo tccutil reset ScreenCapture com.minddragon.bridgesessions
sudo tccutil reset Accessibility com.minddragon.bridgesessions
# Then open System Settings → Privacy & Security → Screen Recording
# Add BridgeSessions.app (or the terminal that launched it)
```

**Alternative: tccutil + AppleScript** (requires user interaction once):
```bash
open "x-apple.systempreferences:com.apple.preference.security?Privacy_ScreenCapture"
```

## Proposed Design: BridgeSessions Menubar Helper (.app)

### Architecture

A **separate Swift menubar app** (`BSMenubar.app`) that:

1. **Manages the cua-helper lifecycle** — launches `bridgesessions --cua-helper` as a child process, restarts on crash
2. **Shows a "B" status item** in the system menubar (NSStatusItem + NSMenu)
3. **Polls fleet status** — runs `bridgesessions fleet` every 5s, parses output, displays in a popover/table view
4. **Settings panel** — autolaunch toggle (writes a LaunchAgent), permissions check button (opens System Settings)

### Why Swift and not C++/ObjC++

- NSStatusItem, NSMenu, NSTableView, NSPopover are all AppKit — Swift is the natural fit
- The menubar app is a **thin shell** — it doesn't implement mesh protocol, just calls the `bridgesessions` CLI
- Keeps the C++ binary focused on the mesh daemon; the Swift app handles only UX
- Can be developed/built on macOS only (Xcode or `swiftc` CLI)

### Autolaunch at login

Two mechanisms:
1. **LaunchAgent** (preferred): `~/Library/LaunchAgents/com.minddragon.bridgesessions.menubar.plist` with `RunAtLoad=true`
2. **SMAppService** (macOS 13+): `SMAppService.mainApp.register()` — the modern API

```swift
// SettingsController.swift
func toggleAutolaunch(_ enabled: Bool) {
    if enabled {
        // Write LaunchAgent plist
        let plist = """
        <?xml version="1.0" encoding="UTF-8"?>
        <plist version="1.0">
        <dict>
          <key>Label</key>
          <string>com.minddragon.bridgesessions.menubar</string>
          <key>ProgramArguments</key>
          <array>
            <string>\(appPath)</string>
          </array>
          <key>RunAtLoad</key>
          <true/>
          <key>KeepAlive</key>
          <false/>
        </dict>
        </plist>
        """
        try? plist.write(toFile: launchAgentPath, atomically: true, encoding: .utf8)
        Process.launchedProcess(launchctl: ["load", launchAgentPath])
    } else {
        try? FileManager.default.removeItem(atPath: launchAgentPath)
        Process.launchedProcess(launchctl: ["unload", launchAgentPath])
    }
}
```

### Permissions check

```swift
func checkPermissions() {
    // Check if Screen Recording is granted by attempting a capture
    let task = Process()
    task.executableURL = URL(fileURLWithPath: "/usr/sbin/screencapture")
    task.arguments = ["-x", "/tmp/bs-perm-check.png"]
    try? task.run()
    task.waitUntilExit()
    
    let img = NSImage(contentsOfFile: "/tmp/bs-perm-check.png")
    let hasPermission = img != nil && img!.size.width > 1
    
    if !hasPermission {
        // Open System Settings to the Screen Recording pane
        NSWorkspace.shared.open(URL(string: 
            "x-apple.systempreferences:com.apple.preference.security?Privacy_ScreenCapture")!)
    }
    
    // Also check Accessibility (for CGEvent input injection)
    let trusted = AXIsProcessTrusted()
    if !trusted {
        // Prompt for Accessibility
        let options: NSDictionary = [kAXTrustedCheckOptionPrompt.takeRetainedValue(): true]
        AXIsProcessTrustedWithOptions(options)
    }
}
```

### Helper process manager

```swift
// HelperProcessManager.swift
class HelperProcessManager {
    private var helperProcess: Process?
    
    func start() {
        guard helperProcess == nil else { return }
        let p = Process()
        p.executableURL = URL(fileURLWithPath: bsBinaryPath)
        p.arguments = ["--cua-helper"]
        p.terminationHandler = { [weak self] _ in
            // Auto-restart after 3s if crashed
            DispatchQueue.main.asyncAfter(deadline: .now() + 3) {
                self?.helperProcess = nil
                self?.start()
            }
        }
        try? p.run()
        helperProcess = p
    }
    
    func stop() {
        helperProcess?.terminate()
        helperProcess = nil
    }
    
    var isRunning: Bool {
        helperProcess?.isRunning ?? false
    }
}
```

## Install Workflow (revised)

### Step 1: Install (one-time)

```bash
# On macOS host:
curl -sL https://bridgesessions.dev/install.sh | bash
# OR from source:
cd ~/bridgesessions && ./install.sh
```

What `install.sh` does on macOS (revised):
1. Copies binary to `~/.local/bin/bridgesessions`
2. Creates `~/.bridgesessions/config` (if missing)
3. Installs launchd daemon: `~/Library/LaunchAgents/com.bridgesessions.mesh.plist`
4. Loads the daemon: `launchctl bootstrap gui/$(id -u) ...`
5. **NEW:** Copies `BSMenubar.app` to `/Applications/`
6. **NEW:** Offers to launch the menubar helper immediately
7. **NEW:** Opens System Settings → Screen Recording for the user to grant permission

### Step 2: Activate (double-click)

User double-clicks **BSMenubar.app** in `/Applications/`:
1. App launches, "B" icon appears in menubar
2. App starts the cua-helper child process
3. App starts fleet status polling
4. If Screen Recording permission is missing, shows a notification: "Click to grant Screen Recording permission"

### Step 3: Settings

User clicks [B] → Settings:
- **Launch at Login** checkbox (default: ✓)
- **Check Permissions** button → opens System Settings if missing
- **Restart Helper** button → kills and relaunches the cua-helper

## Additional Fixes Needed (beyond the user's request)

### Fix 5: `bs cua screen` should propagate errors

**Current:** `bs cua screen peer-mac` returns `0x0` with exit 0 when the helper fails — misleading.
**Fix:** Check `resp.status` in the screen_info client path and print the error string if non-zero.

### Fix 6: Binary source divergence must be resolved

The peer-mac binary (`9a8b229c`) was built from source that doesn't exist in the repo. The macOS helper dispatch code was implemented but **never committed**. This is a source-control failure.

**Action:** Commit the macOS helper dispatch code (the fix from Layer 2) to `main`. Rebuild all macOS binaries from committed source. Replace all fleet macOS binaries with the rebuilt version.

### Fix 7: TCC reset + re-grant after binary update

Every time the binary is replaced, TCC grants are invalidated (adhoc signing). After deploying a new binary:

```bash
# Reset TCC for the old identity
tccutil reset ScreenCapture bridgesessions
tccutil reset Accessibility bridgesessions
# User must re-grant via System Settings
open "x-apple.systempreferences:com.apple.preference.security?Privacy_ScreenCapture"
```

**Long-term fix:** Use a Developer ID certificate for stable signing. The repo has `scripts/sign-macos.sh` ready — it just needs a real certificate.

### Fix 8: launchd plist should not start the helper

The current `com.bridgesessions.mesh.plist` runs the **daemon** only. This is correct — the helper must run in the user GUI session, not under launchd (which may run in a different session context). The menubar app handles helper lifecycle.

But: the plist should be updated to use `$HOME`-relative paths or `~` expansion, not hardcoded `/Users/<operator>/...` paths. The `install.sh` already does this correctly (line 150: `${BIN_ABS}`); the example `com.bridgesessions.mesh.plist` in-tree must stay free of machine-local home paths.

### Fix 9: Capture should use ScreenCaptureKit, not `screencapture` CLI

The helper's macOS capture path (action 6, bs-cua-helper.h:263–287) shells out to `screencapture -x`. This works but:
- Requires Screen Recording permission for `screencapture` (or the calling process)
- Is slower than native ScreenCaptureKit
- Doesn't work in headless/screen-locked states

The `macos-capture.mm` file already implements `bs_macos_capture_png()` using ScreenCaptureKit directly. The helper should call this instead of shelling out:

```cpp
// bs-cua-helper.h, case 6, replace screencapture CLI with:
case 6: {  // capture — ScreenCaptureKit (native, faster)
    char tmp[] = "/tmp/bs-cua-helper-XXXXXX.png";
    int fd = mkstemps(tmp, 4);
    if (fd >= 0) close(fd);
    char err[1024] = {};
    if (bs_macos_capture_png(tmp, 0, err, sizeof(err))) {
        std::ifstream cap(tmp, std::ios::binary | std::ios::ate);
        auto sz = cap.tellg();
        if (sz > 0 && (size_t)sz <= MAX_IMAGE_BYTES) {
            resp.data.resize((size_t)sz);
            cap.seekg(0);
            cap.read((char*)resp.data.data(), sz);
            ::unlink(tmp);
            resp.format = 1; resp.status = 0;
            auto r = CGDisplayBounds(CGMainDisplayID());
            resp.screen_w = (int16_t)r.size.width;
            resp.screen_h = (int16_t)r.size.height;
            return resp;
        }
    }
    ::unlink(tmp);
    resp.status = 1;
    resp.error = std::string("ScreenCaptureKit failed: ") + err;
    return resp;
}
```

**Note:** `bs_macos_capture_png` is defined in `macos-capture.mm` and linked into the binary (CMakeLists.txt:57). The helper code in `bs-cua-helper.h` is included by `main.cpp`, so the function is available at link time. Need to add `extern "C" int bs_macos_capture_png(...)` declaration in the helper header.

### Fix 10: Token rotation race condition

The helper generates a fresh token on each start (bs-cua-helper.h:308–320). If the helper restarts while the daemon has a cached token, the daemon will fail auth until it re-reads the token file. The current code reads the token per-RPC (line 2953–2958), so this is not a live bug — but it's worth documenting that the helper must NOT restart without the daemon knowing.

The menubar app's auto-restart (HelperProcessManager) will cause a brief auth failure window (~1s) during helper restart. The daemon will fall back to in-process (which fails on macOS), then succeed once the helper is back. This is acceptable.
