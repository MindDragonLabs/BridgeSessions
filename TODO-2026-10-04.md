### B4. Acceptance-harness flake — **REOPENED, original premise was wrong**

**The 3s-vs-12s story was incorrect.** `should_defer_outbound_for()` does not
wait 12s and then dial. On expiry it **extends exponentially**, and only after
the extension budget is exhausted does it allow one probe:

| ext | window | cumulative | state |
|---|---|---|---|
| 0 | 12s | 12s | deferring |
| 1 | 24s | 36s | deferring |
| 2 | 48s | 84s | deferring |
| 3 | 96s | 180s | deferring |
| 4 | 192s | 372s | deferring |
| 5 | 384s | 756s | deferring |

The first outbound attempt is **756s** away, not 12s. No budget below that can
pass, and 756s would blow the 120s ctest timeout set in `e800604` and turn a
real failure into a silent kill.

**Measured, not inferred** — 10 consecutive runs, no retry-until-pass:

```
run  1: PASS (6s)     run  6: PASS (6s)
run  2: PASS (6s)     run  7: PASS (6s)
run  3: FAIL (37s)    run  8: PASS (6s)
run  4: PASS (6s)     run  9: PASS (6s)
run  5: FAIL (38s)    run 10: FAIL (38s)
=== 7 pass / 3 fail out of 10 ===
```

**What landed in `d883292` and is worth keeping:** read-only accessors for the
tie-break constants (product behaviour byte-for-byte unchanged), poll loops
that derive from the product window instead of magic numbers, and a failure
message that names the real cause. The e2e now fails 3 of 3 with an actionable
diagnostic instead of flaking quietly. The other 619 tests pass.

**Do not close this by raising the timeout.** That hides the race behind a 756s
test. The real fix is product-side and needs a decision:

- Guarantee the smaller-pubkey side initiates in this scenario, **or**
- Have the test pin an explicit connection direction so the tie-break never
  decides.

Either way `kTieBreakAcceptWindowMs` stays at 12000.

management.
