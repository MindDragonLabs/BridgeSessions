### B4. Acceptance-harness flake — **DONE (`9bf66a7`), 10/10**

**The 3s-vs-12s story was wrong, and so was my own first correction.** The real
cause was neither a test budget problem nor a product tie-break race.

`should_accept_only_for()` defers outbound dials for the **larger** pubkey and
relies on the smaller-pubkey side to originate. The harness seeded **only**
`panel-a` with `panel-b`:

| pubkey order | panel-a is | behaviour | result |
|---|---|---|---|
| `a.pubkey < b.pubkey` | smaller | dials | works |
| `b.pubkey < a.pubkey` | larger | defers, and `panel-b` has no seed to dial back | **stall** |

Half the key space is a coin flip, and gossip rescued some of the losing runs.
That is the 3-in-10.

**Fix (option 2): seed both directions.** Whichever side holds the smaller
pubkey now always has an entry to dial, so the tie-break decides the direction
instead of which node was configured first. `kTieBreakAcceptWindowMs` stays
12000 and `bs-mesh-conn.h` is untouched.

```
run  1: PASS (11s)   run  6: PASS (11s)
run  2: PASS ( 6s)   run  7: PASS (11s)
run  3: PASS ( 6s)   run  8: PASS ( 6s)
run  4: PASS (12s)   run  9: PASS (11s)
run  5: PASS ( 6s)   run 10: PASS (11s)
=== 10 pass / 0 fail out of 10 ===
```

**A slowdown I introduced, then fixed.** Symmetric seeds alone made runs take
36-52s. Cause was startup order: `db.ready()` blocks until panel-b answers, so
panel-b burned its whole `startup_network_wait` budget (30s,
`retry_delay_secs=10` at `bs-mesh-cli.h:1625`) retrying a seed for panel-a that
was not listening yet. Forking both daemons before waiting on either brought it
back to 6-12s.

**Two traps, recorded so nobody repeats them:**

1. **Use `build/test/bridgesessions`, not `dist/`.** `dist/` held a binary from
   21:58 the previous day that predates session control and fails every run
   with `ERROR invalid machine`. This cost me a false 0/10 "regression". The
   ctest registration passes `$<TARGET_FILE:bridgesessions>` and is unaffected.
2. **`~Root()` deleted the staging tree on exit**, so a failed run left no logs
   to inspect. `BS_KEEP_TEST_ROOT=1` now preserves it and prints the path.

Full default `ctest`: **619/619 + the e2e, 100%.**

### S2. Full mesh trust must not reach phones — **PARTIAL: audit added, enrolment missing**

| requirement | state |
|---|---|
| scoped per-device credentials | **present** — `DEVICE_SCOPES`, `issue_api_token(label, scopes, ttl)` |
| revocation | **present** — `revoke_api_token`, enforced in `credential_scope` |
| expiry | **present** — `expires_at` checked with `time.time()` on every lookup |
| audit events | **WAS ABSENT — added in `6b55fb7`** |
| **enrolment** | **STILL MISSING** |

The gate asks for all four. Three were already there; **audit was missing
entirely** and is now implemented: `audit()`, `read_audit()`,
`audit_log_path()`, writing `auth-audit.log` at 0600 next to the token store.
Issue and revoke emit `token_issued` / `token_revoked` carrying id, label,
scopes and expiry — **never the token value**, since the log is on disk.
Covered by `test_audit_trail_records_credential_lifecycle` (including a
`0600` mode assertion and a no-secret assertion) and
`test_audit_survives_a_malformed_line`.

**Enrolment is not implemented and is not started.** There is no
`enroll_device`, no device registry, and no binding between a credential and a
physical device. Today a token is issued by an admin and handed over out of
band, so "a phone must never get mesh access" is enforced only by the scopes
being narrow, not by the device being enrolled. **This is a real gap against
the stated gate** and needs its own unit.

Also verified while auditing: `credential_scope` uses `hmac.compare_digest`
for token comparison, and revoked/expired rows are skipped before any
comparison, so a revoked credential cannot be probed by timing.

and is named; the redaction literal does not; codename-only-in-code passes with

## Test-coverage defect found while closing Phase 4 (not in the original gate)

**Three pytest files in `tests/` have never run in CI**, and one of them guards
the exact code path S1 cleared.

| file | tests | status |
|---|---|---|
| `test_generate_invite_page.py` | 8 | **never registered in CMake** |
| `test_install_transaction.py` | 4 | **never registered in CMake** |
| `test_release_integrity.py` | 5 | **never registered in CMake** |

All 17 pass when run directly. They were simply not wired into any `add_test`.

`test_generate_invite_page.py` matters most: it is the test backing **S1's C5
finding** that invite tokens travel in a 0600 file rather than a URL, plus
unsafe node-name rejection. I cleared C5 by reading code; this is the test that
would have caught a regression, and it has never executed.

**Root cause is broader than three missing `add_test` calls.** `CMakeLists.txt`
gates the entire Python block on `execute_process(COMMAND python3 -c "import
pytest")` against a `find_program`-resolved interpreter. When that interpreter
lacks pytest — as the system `python3` does here — **the whole block is
skipped silently**, so the *already-registered* `release_python_tests`,
`panel_typing_latency`, `panel_chained_relay` and
`panel_daemon_restart_disconnect` disappear too. This is the same
missing-pytest condition grok found in Phase 3, and the same class of defect as
U1's unregistered `test_tui_pty.py`.

Registered the three files. Verified with a real configure and run:

```
Test #73: panel_generate_invite_page .......   Passed    0.34 sec
Test #74: panel_install_transaction ........   Passed    0.56 sec
Test #75: panel_release_integrity ..........   Passed    0.77 sec
100% tests passed out of 3
```

**Still open:** the silent-skip gate itself. A missing pytest dependency should
be a configure-time warning, not a quiet reduction in coverage. Whether to make
it fatal, or to provision pytest for the test interpreter, is a decision for the
operator — the current behaviour is a green build that silently runs fewer
tests than the tree contains.
